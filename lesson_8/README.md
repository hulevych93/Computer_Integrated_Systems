## Що вивчаємо

- конструкція `with open`: ім'я файлу, режим, кодування
- чому `encoding="utf-8"` вказують завжди
- `write` не додає перехід рядка — символ `\n` ставимо самі
- два способи читання: `read` цілком і прохід циклом по рядках
- `strip` для прибирання `\n` у кінці рядка
- режими `"r"`, `"w"`, `"a"` і чому `"w"` небезпечний
- формат CSV: `DictWriter`, `DictReader`, параметр `newline=""`
- `encoding="utf-8-sig"` і `delimiter=";"` для CSV — щоб файл коректно відкривався в Excel
- усі значення з CSV приходять рядками — типи треба відновлювати
- формат JSON: `json.dump` і `json.load`, збереження типів
- коли обирати CSV, а коли JSON
- шляхи: відносний, `pathlib.Path`, перевірка `exists()`

## Головна ідея заняття

Дані ззовні завжди приходять текстом. Це вже було з `input()` на
другому занятті, тепер те саме повторюється з файлами й CSV.
Перетворення типу — обов'язковий крок, без якого сума значень
перетвориться на склеювання рядків.

Структура з сьомого заняття — список словників — лягає у CSV
без жодної переробки: `DictWriter` сам розставляє значення
по стовпцях за ключами.

## Два налаштування CSV для Excel

Файл, записаний зі звичайним `encoding="utf-8"`, Python прочитає
правильно, а Excel — ні: кирилиця перетвориться на набір знаків
виду `–ù–û–†–ú–ê`. Файл при цьому не зіпсований — Excel просто
не вгадав кодування.

Розв'язання: записувати CSV з `encoding="utf-8-sig"`. Цей режим
додає на початок файлу службову мітку, за якою Excel упізнає UTF-8.

```python
# запис
with open("journal.csv", "w", encoding="utf-8-sig", newline="") as f:
    ...

# читання — теж utf-8-sig
with open("journal.csv", "r", encoding="utf-8-sig", newline="") as f:
    ...
```

Читати теж треба в режимі `utf-8-sig`: він працює і з файлами
з міткою, і без неї. Якщо прочитати файл із міткою звичайним
`utf-8`, перший ключ словника стане `'\ufeffn'` замість `'n'`,
і звернення `row["n"]` впаде з `KeyError` — помилка, причину
якої на екрані не видно.

Для JSON і звичайних текстових файлів мітка не потрібна:
там лишається `encoding="utf-8"`.

### 2. Розділювач стовпців

Друга проблема виглядає так: кодування вже правильне, кирилиця
читається, але **весь рядок потрапляє в один стовпець A**.

Назва формату означає «значення, розділені комами», проте Excel
бере розділювач із системних налаштувань. В українській локалі
десятковий роздільник — кома, тому роздільником списку Excel
вважає **крапку з комою**. Файл із комами він не розбирає.

Розв'язання: писати й читати CSV із `delimiter=";"`, винісши
його в сталу, щоб міняти в одному місці:

```python
DELIMITER = ";"

writer = csv.DictWriter(f, fieldnames=FIELDS, delimiter=DELIMITER)
...
for row in csv.DictReader(f, delimiter=DELIMITER):
```

Розділювач при читанні має бути такий самий, як при записі.
Якщо прочитати файл із крапкою з комою без `delimiter`, вийде
один ключ із цілим рядком усередині:

```
{'n;value;state': '1;20.0;НОРМА'}
```

Це той самий симптом, що й один стовпець у Excel, тільки видно
його з боку програми.

## Контрольна серія

**20, 25, 70, 18, 150** при уставках `min = -40`, `max = 60`,
`alarm = 100`.

Вміст `journal.csv` після збереження:

```
n;value;state
1;20.0;НОРМА
2;25.0;НОРМА
3;70.0;ПОПЕРЕДЖЕННЯ
4;18.0;НОРМА
5;150.0;АВАРІЯ
```

Середнє по журналу — **56.600**. Те саме значення має вийти після
читання файлу назад: саме це й доводить, що дані відновлено без втрат.

## Домашнє завдання

Одне завдання на дві теми — словники (заняття 7) та файли (заняття 8).

Умова — у файлі `kik-praktykum/praktyka_07_08/task_07_08.py`.

Чотири частини, що утворюють один наскрізний ланцюг:

1. **Довідник датчиків** — словник словників, збереження й читання
   у форматі JSON, додавання нового каналу.
2. **Класифікація за паспортом** — межі беруться з паспорта датчика,

3. **Реєстратор** — за один запуск додає один вимір до журналу
   у CSV; наступний запуск продовжує з того місця, де зупинився.
4. **Зведення по каналах** — підсумок по кожному каналу окремо
   та збереження звіту у JSON.

Вперше ставиться вимога: програма має коректно працювати при
**повторних запусках**, а не лише з чистої теки.
